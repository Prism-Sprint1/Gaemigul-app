# 담당 업무: 메인 페이지 백엔드 (timeline 도메인)

> 이 문서는 작업을 재개할 때 가장 먼저 읽는 문서다. 새 작업을 시작하기 전에 '다음 작업'과
> '결정된 설계 방향'을 확인하고, 작업이 끝나면 바뀐 내용을 여기에 반영한다.

## 담당 범위

- 메인 페이지 백엔드 구현 (`src/backend/domain/timeline`)
- 실사용 API(한국투자증권, 네이버 뉴스 등) 데이터 확인 및 기획된 기능의 구현 가능 여부 검증
- 프로젝트 진행 중 미흡한 부분 지원

## 메인 페이지 구성 (내 작업 대상)

- **최상단 지표 바**: 코스피, 코스닥, 니케이, 달러 환율, S&P500, 나스닥 — 모든 페이지 공통 고정 영역이지만 데이터는 이 도메인에서 제공. **구현 완료**
  - ~~나스닥 선물, 유가, 금~~ 은 제외함. 한국투자증권 API로 조회는 되지만, 지금 쓰는 계좌에 CME/NYMEX/COMEX 거래소 이용 권한이 없어서 호출하면 에러가 남(계좌 권한 문제라 코드로 해결 불가)
- **좌측 사이드바**: 실시간 타임라인 피드. 사이드바 껍데기는 전 페이지 고정이고, 캘린더/히트맵 페이지로 이동 시 내부 콘텐츠만 바뀜(다른 도메인 담당)
- **메인 섹션(시황 탭)**: 8개 시간대 타임라인 콘텐츠. **수집·LLM 생성·DB 저장·조회·스케줄러 구현 완료**
- **메인 섹션(브리핑 탭)**: AI가 당일 시황 데이터로 일간 보고서 작성 → 그 주 일간 보고서를 모아 주간 보고서 작성. **미착수**

## 브랜치

- `back/feat/timeline` 에서 작업 (main 기준으로 분기)

## 기술 스택

- FastAPI, uv
- DB: Supabase PostgreSQL — SQLAlchemy 비동기 ORM(asyncpg 드라이버)으로 연결. **연동 완료**
  - 연결 문자열은 `.env`의 `DATABASE_URL`로 관리(커밋 금지)
  - Supabase가 주는 문자열은 `postgresql://`로 시작하므로 `postgresql+asyncpg://`로 바꿔서 넣어야 함

## 메인 콘텐츠(시황 탭) 데이터 구성

하루 8개 시간대 슬롯으로 구성. 시간대별 화면 명칭은 고정 문구라 프론트에서 매핑한다.

| 시간대 | 명칭 |
|---|---|
| 07:30 | 글로벌 시황 |
| 08:30 | NXT 프리마켓 |
| 09:30 | 장초반 흐름 |
| 12:00 | 오전장 흐름 |
| 14:00 | 오후장 흐름 |
| 15:30 | 장 마감 |
| 17:30 | 애프터마켓 |
| 20:00 | 오늘 시장 분석 |

**모든 슬롯 공통**

1. LLM 브리핑 — 타이틀, 부제 + 요약(타이틀 + 설명) 3개
2. 주린이 해설 — 타이틀, 내용, 태그 3개 (같은 내용을 주식 입문자용으로 쉽게 풀어쓴 것)
3. 주요 뉴스 — 타이틀, 설명, 링크 (네이버 뉴스 API 사용, AI가 주요 뉴스만 선별)
4. 네 번째 칸은 슬롯에 따라 내용이 다르다 (정규장 안/밖)

| 슬롯 | 네 번째 칸 |
|---|---|
| 09:30 / 12:00 / 14:00 / 15:30 | **주도 섹터** — 코스피 업종 등락률 TOP3 |
| 08:30 / 17:30 / 20:00 | **급상승 종목 TOP3** — 종목명·등락률·가격 |
| 07:30 | 없음 (지표 6종이 그 자리를 대신한다) |

- 주도 섹터: 섹터명·등락률 + 섹터 내 상승 1위/거래대금 1위 종목(종목명·등락률).
  상승 1위와 거래대금 1위가 같은 종목이면 "상승·거래 1위"로 합쳐 표기
- 급상승 종목: 정규장 밖에는 업종 지수가 산출되지 않아 주도 섹터를 만들 수 없다(실측 확인).
  대신 종목 단위 데이터는 살아 있어서 급상승 TOP3로 대체했다. **상승만 보여주고 하락은 넣지 않는다**
  - 세 슬롯 모두 **넥스트레이드(`market_div_code="NX"`)** 에서 뽑는다.
    08:30은 NXT 프리마켓(08:00~08:50), 17:30 / 20:00은 NXT 애프터마켓(15:40~20:00)
  - **API가 준 순서를 믿지 않고 등락률로 다시 정렬한다.** NX 응답의 `data_rank`가
    등락률 내림차순이 아니다(2026-09-12 실측: 1위 영풍 +26.40% / 2위 에스투더블유 +29.96%).
    거래소(J)는 상위 30개가 전부 29.8~30.0%로 정상이라 NX만의 문제다.
    30행을 받아 `prdy_ctrt` 내림차순으로 정렬한 뒤 상위 3개를 쓴다

**특정 슬롯 전용**

- 07:30 — 어제 마감 & 글로벌 현황: 지표 6종(코스피/코스닥/나스닥/S&P500/니케이/환율)의 명칭·가격·등락폭
- 15:30 — 장중 변화: 코스피/코스닥/환율 3종의 명칭·07:30 가격·마감 가격·변동폭

## DB 스키마 (Supabase 생성 완료)

```
timeline_slot ──┬── timeline_briefing_insight    LLM 요약 3행
                ├── timeline_beginner_guide      주린이 해설 3행
                ├── timeline_news                뉴스 5~8행
                ├── timeline_indicator           지표 6종 (07:30 슬롯만)
                ├── timeline_intraday_change     장중 변화 3종 (15:30 슬롯만)
                ├── timeline_top_gainer          급상승 종목 3행 (08:30 / 17:30 / 20:00)
                └── timeline_leading_sector      섹터 3행 (09:30 / 12:00 / 14:00 / 15:30)
                        └── timeline_leading_sector_stock   종목 1~2행
```

- 테이블 9개. 하루에 `timeline_slot` 8행이 쌓이고, 나머지 테이블은 슬롯 id를 FK로 물고 붙는다
- 모든 테이블에 `created_at`이 있고 **한국 시간(naive KST)으로 저장한다.** 파이썬 기본값과
  DB `DEFAULT (now() AT TIME ZONE 'Asia/Seoul')`을 둘 다 걸어뒀다(한쪽만 있으면 서버가
  옛 코드일 때 NOT NULL 위반이 난다 — 실제로 슬롯 3개를 날린 적이 있다)
- `trade_date` + `time_slot` 조합에 유니크 제약 (같은 날 같은 시간대 중복 저장 방지)
- 하루 전체 약 217행 / 연간 약 5만 행 수준 — 용량·성능상 문제 없음
- 브리핑 탭(일간/주간 보고서)은 슬롯에 속하지 않으므로, 구현 시 `timeline_daily_report` / `timeline_weekly_report` 테이블을 별도로 추가하면 됨

**API 엔드포인트는 테이블 수와 무관하다.** 화면이 하루 단위로 렌더링되므로 `GET /timeline?date=...` 하나로 8슬롯 전체를 중첩 JSON으로 내려주고, 여러 테이블을 읽어 조립하는 것은 services 계층이 담당한다.

## 데이터 확보 검증 결과 (실제 호출로 확인 완료)

### 주도 섹터 — KIS API 3개 조합

| 용도 | 엔드포인트 | TR ID |
|---|---|---|
| 업종 목록(코스피 전체) | `/uapi/domestic-stock/v1/quotations/inquire-index-category-price` | `FHPUP02140000` |
| 업종 내 등락률 순위 | `/uapi/domestic-stock/v1/ranking/fluctuation` | `FHPST01700000` |
| 업종 내 거래대금 순위 | `/uapi/domestic-stock/v1/quotations/volume-rank` | `FHPST01710000` |

- 업종 목록에서 등락률 TOP3를 뽑고, 각 업종코드로 종목 순위를 조회하는 방식
- 순위 API 두 개 모두 `FID_INPUT_ISCD`에 업종코드를 넣으면 그 업종 안에서만 순위가 나옴
- 슬롯당 호출 7회(업종 목록 1 + TOP3 x 2), 하루 8슬롯 기준 56회

호출해보고 알게 된 것들:

1. 업종 목록은 등락률 순으로 정렬돼서 오지 않는다. 업종코드 순서로 오므로 정렬은 받는 쪽에서 해야 한다.
2. **주도 섹터는 코스피만 쓴다. 이유는 아래 '코스닥 업종 재검토'에 적었다.**
   (이전 기록 정정: "코스닥은 파생지수만 나오고 실제 업종은 '오락·문화' 하나뿐"이라고 적었는데
   틀렸다. 실제 업종 21개가 다 있다. 못 쓰는 이유는 응답이 불안정한 것이다.)
3. 코스피 38행에도 업종 아닌 것이 섞여 있다. `종합`/`대형주`/`중형주`/`소형주`, `제조`(대분류), `VKOSPI`(변동성 지수), 각종 전략지수. 걸러내지 않으면 "주도 섹터 1위: 종합"이 나온다. 쓸 업종 21개는 `leading_sector_service.py`의 `KOSPI_SECTOR_CODES`에 화이트리스트로 고정.
4. `금융`(0021)은 `증권`(0024)·`보험`(0025)의 상위 분류다. 금융 업종의 종목 순위를 조회하면 증권사·보험사·지주회사가 같이 나온다. KRX 업종분류가 통계청 표준산업분류를 따르기 때문(금융업 아래 은행/증권/보험/기타금융). 셋 다 넣으면 TOP3에 금융과 증권이 나란히 떠서 같은 얘기를 두 번 하게 되므로 증권·보험을 뺐다.
5. 시장 전체가 빠지는 날은 TOP3가 모두 마이너스로 나온다. 정상이며 세시반도 같은 방식으로 표시한다(하락장에서 '주도 섹터'에 마이너스 값 노출 확인). 부호 처리는 프런트에서 `change_rate`가 0보다 큰지 작은지로 나눈다.

### 코스닥은 쓰지 않는다 — 재검토 결과 (2026-09-12)

"인버스 같은 걸 걸러내고 섹터만 뽑아 코스피·코스닥을 합치면 어떤가"를 확인했다.
**결론: 기술적으로 가능하지만 코스피만 쓴다.** 근거 네 가지다.

**① 코스닥 업종 목록이 호출마다 바뀐다 (결정적)**

`FID_MRKT_CLS_CODE=Q` / `FID_INPUT_ISCD=1001`로 조회하면 **항상 정확히 100행**이 오는데,
그 100행의 구성이 매번 다르다. 5회 연속 호출한 결과다.

```
1~3회  100행 중 코스닥 업종  0개
4회    100행 중 코스닥 업종  3개
5회    100행 중 코스닥 업종 13개
       5회 합집합 16개 / 교집합 0개   <- 5회 모두에 나온 업종이 하나도 없다

대조군: 코스피(K/0001) 3회 -> 38행 매번 동일
```

100행 상한에 걸려 잘리는데 **잘리는 지점이 움직인다.** `tr_cont`가 비어 있어 연속조회도 없다.
목록이 매번 달라지면 TOP3 순위를 신뢰할 수 없다.

**② 우회로는 있지만 호출이 4배**

업종코드를 상수로 박고 `get_domestic_index_price("U", 코드)`로 하나씩 찌르면 **26개 전부 조회된다**
(등락률·가격 정상, 종목 순위도 정상 — `1028` -> 앤씨앤/우리기술 실측). 하지만 목록 1회로 끝나는
코스피와 달리 업종마다 1회씩 필요하다.

```
지금    슬롯당  7회      합치면  슬롯당 28회
```

KIS는 초당 한도를 넘기면 HTTP 500 + `EGW00201`을 준다. 지금도 7회 연속에서 걸린 적이 있다.

**③ 업종명 21개 중 19개가 겹친다**

개별 지수 조회는 `hts_kor_isnm`이 **빈 값**으로 와서 이름을 상수로 들고 있어야 한다
(이름을 모으려고 목록 API를 8번 불러 합집합을 만들었다). 그런데 이름이 이렇게 겹친다.

```
겹치는 19개  일반서비스 건설 유통 운송·창고 금융 오락·문화 음식료·담배 섬유·의류 종이·목재
             화학 제약 비금속 금속 기계·장비 전기·전자 의료·정밀기기 운송장비·부품 통신 IT 서비스
코스닥에만   출판·매체복제, 기타제조      코스피에만   전기·가스, 부동산
```

"주도 섹터: 금융 +1.79%"가 어느 시장인지 알 수 없다. 오늘 금융은 코스피 +1.79% / 코스닥 -2.11%로
**부호가 반대**였다. 모든 섹터명에 시장 이름을 붙여야 하고, 그러면 화면 스펙이 바뀐다.

**④ 합치면 코스닥이 TOP3를 잠식한다**

```
등락률 폭   코스피 4.56%p / 코스닥 5.99%p

합친 TOP3   코스닥 출판·매체복제 +2.01%  /  코스피 건설 +1.90%  /  코스닥 오락·문화 +1.50%
            -> 3자리 중 2자리가 코스닥
```

시가총액이 작고 변동성이 큰 코스닥 업종이 상위를 채우면 **"주도 섹터"가 시장을 대표하지 못한다.**
합치는 목적 자체가 흔들린다.

**대안이 필요해지면** 합치지 말고 코스피 TOP3 / 코스닥 TOP3를 따로 보여주는 쪽이 낫다.
이름 중복과 잠식 문제가 둘 다 사라진다. 지표 바에 코스닥 종합이 이미 있어서 화면에서 빠지는 것도 아니다.

쓸 수 있는 코스닥 업종코드 (쓰게 되면 그대로 상수로 박으면 된다):

```
1006 일반서비스  1010 건설      1011 유통      1013 운송·창고   1014 금융
1015 오락·문화   1019 음식료·담배 1020 섬유·의류  1021 종이·목재   1022 출판·매체복제
1023 화학       1024 제약      1025 비금속    1026 금속       1027 기계·장비
1028 전기·전자   1029 의료·정밀기기 1030 운송장비·부품 1031 기타제조  1032 통신
1033 IT 서비스

제외: 1001 KOSDAQ(종합) / 1002~1004 대형·중형·소형주 / 1009 제조(대분류)
      1042~1045 우량·벤처·중견·기술성장기업 / 1049 코스닥 글로벌
```

참고로 레퍼런스인 세시반의 "업종" 카드는 `핸드셋` / `소프트웨어` / `조선`처럼 더 세분화된
분류를 쓴다(FnGuide 계열). KIS는 KRX 표준 업종분류만 주므로 우리 카드는 `전기·전자` /
`기계·장비`처럼 더 큰 단위다. 화면 구성이 같아도 업종명의 세밀함은 다를 수밖에 없다.

### 뉴스 — 네이버 뉴스 검색 API

- 제공 필드: `title` / `description` / `link` / `originallink` / `pubDate`. 언론사명·썸네일은 없음
- **검색어가 필수다.** "이 시간대 주요 뉴스"를 주는 API가 아니라, 우리가 넣은 검색어에 맞는 기사만 준다. 그래서 슬롯별 검색어를 `news_service.py`의 `_SLOT_KEYWORDS`에 표로 정해뒀다
- **정렬은 반드시 `sort="sim"`(정확도순).** 기본값 `date`(최신순)는 관련도를 거의 안 봐서 '시간외 거래'로 검색하면 게임 기사가, '시황'으로 검색하면 증권사 신제품 기사가 나온다
- **슬롯마다 그 시간대에 나온 기사만 담는다.** 모든 슬롯을 "최근 24시간"으로 두면 09:30과 12:00 슬롯이 10건 중 9건 같은 기사를 보여준다(실측).
- **구간은 `[직전 슬롯, 이 슬롯)`** — 시작은 포함, 끝은 배타다(07:30만 전날 20:00부터 — 밤사이 해외장 기사를 담아야 해서). 양쪽을 포함으로 두면 슬롯 시각 정각 기사가 두 슬롯에 중복됐다(08:30:00 기사가 08:30 슬롯과 09:30 슬롯에 둘 다). pubDate가 분 단위라서(표본 400건 전부 초가 `00`) 실제로는 이렇게 잘린다.

  ```
  07:30  전날 20:00 ~ 07:29     08:30  07:30 ~ 08:29
  09:30  08:30 ~ 09:29          12:00  09:30 ~ 11:59
  14:00  12:00 ~ 13:59          15:30  14:00 ~ 15:29
  17:30  15:30 ~ 17:29          20:00  17:30 ~ 19:59
  ```
- **무엇을 남길지는 최신순이 아니라 중요도 점수로 정한다.** 07:30은 구간이 11시간이 넘어서, 최신순으로 자르면 밤사이 나온 중요한 기사가 아침의 자잘한 기사에 밀려 잘려나간다. 점수는 검색어별 정확도 순위를 `1/(60+순위)`로 바꿔 합산한 값이다. 여러 검색어에 동시에 걸린 기사일수록, 각 검색어에서 위에 있을수록 높아진다. 남길 것을 고른 뒤 화면 순서는 최신순으로 되돌린다
- 이 점수는 순위를 합칠 뿐 내용의 중요도를 판단하지는 못한다. 스펙상 최종 형태는 'AI가 주요 뉴스만 선별'이므로, LLM을 붙일 때 후보를 넉넉히 넘겨 고르게 하는 단계를 추가한다
- `link`와 `originallink`는 같은 값이 아니다. `originallink`는 항상 언론사 원문이고, `link`는 네이버 제휴 기사면 `n.news.naver.com` 주소, 아니면 원문 주소다. 60건 표본에서 네이버 도메인은 25%였다. **`link`를 쓰되 없으면 `originallink`로 넘긴다**
- 검색어 고르는 기준: 단어가 짧고 하나일수록 잘 맞는다. `개장시황`/`마감시황`처럼 기사 제목 말머리로 실제 쓰이는 말이 정확도가 높다. `환율`처럼 일상어이기도 한 단어는 제품 가격 기사를 물어오므로 `원달러 환율`로 좁힌다
- 슬롯당 **최소 5건 / 최대 8건**을 싣는다(`news_service._PICK_MIN` / `_PICK_MAX`).
  상한은 처음 10건이었는데 화면 스크롤이 길어져서 8로 줄였다(2026-09-12).
  `timeline_service._NEWS_LIMIT`이 `_PICK_MAX`를 그대로 가져다 쓰므로 고칠 곳은 한 군데다
- 호출량은 슬롯당 검색어 5~6개 x 8슬롯 = 하루 40~48회. 한도 25,000회 대비 여유가 크다

### 지표 6종

지표 바에서 이미 10분마다 수집 중인 값을 그대로 쓴다.

## 정규장 밖 데이터 (07:30 / 08:30 / 17:30 / 20:00 슬롯)

결론부터. **업종 지수는 정규장에만 돌고, 종목 데이터는 정규장 밖에도 산다.**
그래서 이 네 슬롯은 주도 섹터를 만들 수 없고, 대신 급상승 종목 TOP3를 쓴다.

### 업종 지수는 정규장 밖에 멈춘다 (실측)

```
업종 목록 API(FHPUP02140000)  시장구분코드 U만 받는다
                              NX(넥스트레이드) / UN(통합) / J는 전부
                              ERROR INVALID FID_COND_MRKT_DIV_CODE

애프터마켓  2026-09-10 23:36 조회 -> 코스피 마지막 체결이 15:32:00
            KRX 시간외단일가(16:00~18:00)를 다 지나서 조회했는데도 마감에 멈춰 있다
프리마켓    2026-09-11 07:46(프리마켓 전)과 08:56(프리마켓 후) 두 번
            둘 다 마지막 체결 없음, 업종 21개 등락률 전부 0.00%로 동일
```

거래소가 업종 지수를 정규장에만 산출하기 때문이지 API 한계가 아니다.

주의: 업종 시간별지수(`FHPUP02110200`)는 체결이 없는 자리를 `99:99:99` 같은 더미 값으로 채워
보낸다. **시(hour) 자리가 00~23이 아닌 행은 걸러야 한다**(분봉에서 본 `88:88`과 같은 현상).
그리고 지금 시점부터 거슬러 최근 100틱만 주므로 **과거를 소급 조회할 수 없다.**

### 종목 데이터는 넥스트레이드로 조회된다

2026-09-11 정규장 중에 시장구분코드를 바꿔가며 확인했다. 넥스트레이드는 정규장에도 같이
거래되므로, 값이 다르게 나오면 실제로 따로 조회된다는 뜻이다.

```
주식현재가     삼성전자   J=5,756,692주  NX=4,329,410주  UN=10,086,114주  <- UN = J + NX
등락률 순위    전기·전자  J=삼화콘덴서 21.18%      NX=솔루스첨단소재 16.40%
거래대금 순위  전기·전자  J=SK하이닉스 1,161,734주 NX=SK하이닉스 760,290주
업종 지수                U만 정상
```

**이 결과로 급상승 종목 TOP3를 구현했다**(`top_gainer_service.py`). 08:30은 NXT 프리마켓,
17:30 / 20:00은 NXT 애프터마켓에서 뽑는다.

(이전 기록 정정: 2026-09-10에 "J와 NX 결과가 같아서 NXT가 무시되는 것 같다"고 적었는데 틀렸다.
그날은 장 마감 후라 NXT도 멈춰 있어서 같아 보였던 것이다. **시장구분 파라미터는 그 값이
유효한 시간대에 테스트해야 한다.**)

### 안 쓰기로 한 것들 (응답은 확인함)

급상승 종목을 NXT 등락률 순위로 만들기로 해서 아래는 쓰지 않는다. 나중에 필요해지면 여기서 시작한다.

| API | TR ID | 비고 |
|---|---|---|
| 예상체결 상승/하락 순위 | `FHPST01820000` | 30행. 08:30 대체 수단으로 코드에 남겨둠 |
| 국내주식 시간외현재가 | `FHPST02300000` | 응답 확인 |
| 국내주식 시간외호가 | `FHPST02300400` | 응답 확인 |
| 주식현재가 시간외일자별주가 | `FHPST02320000` | 최근 30거래일 시간외 종가·거래량 |
| 예상체결가 추이 | `FHPST01810000` | 응답 확인 |

**KRX 시간외 데이터는 종목 편차가 크다.** 시간외일자별주가로 6개를 확인해보니 카카오만 거래량이
잡히고(최근 5거래일 2,967~14,408주) 삼성전자·SK하이닉스·현대차는 30거래일 내내 0이었다.
NXT를 쓰는 이유가 이것이다.

한국거래소 애프터마켓이 2026-09-14부터 오후 4~8시로 열린다는 보도가 있다(미확인).
열리면 `UN`(통합) 값이 달라질 수 있으므로 17:30 슬롯을 재확인할 것.

## 최상단 지표 바 — 동작 순서

### 휴장일에는 갱신하지 않는다 — 국내 지표만 (2026-09-12)

`is_market_open()`이 국내 지표에 대해 **주말 -> 국내 휴장일 -> 개장 시간** 순으로 본다.
전에는 주말만 봐서 추석 같은 공휴일에도 10분마다 KIS를 불렀다.

| 지표 | 휴장일 판정 |
|---|---|
| 코스피 / 코스닥 | 국내휴장일 조회(`CTCA0903R`)의 `opnd_yn` |
| 니케이 / 나스닥 / S&P500 | 보지 않음 (주말 + 개장 시간만) |
| 환율 | 없음 — 항상 갱신 |

판정 결과(실측):

```
                    kospi  kosdaq  nikkei  nasdaq
금 10:00 국장 중          O       O       O       X
금 23:30 미장 중          X       X       X       O
토 10:00                X       X       X       X
추석(목) 10:00           X       X       O       X
```

국내 판정은 스케줄러가 이미 쓰는 `is_trading_day()`를 그대로 재사용한다. 캐시도 공유하므로
새로 드는 호출이 없다.

### 해외 공휴일은 보지 않는다 (검토 후 제외)

KIS에 해외 개장일을 알 수 있는 API가 있다. **`CTOS5011R` "해외결제일자조회"**
(`/uapi/overseas-stock/v1/quotations/countries-holiday`). 개장 여부 필드는 없지만
**거래가 있는 시장만 행으로 오는** 성질을 쓰면 판정이 된다. 실측으로 확인까지 했다.

```
2026-09-11(금)  17행  US JP HK CN GB VN     평범한 개장일
2026-09-12(토)   0행                       주말
2026-09-23(수)  16행  US HK CN GB VN        일본 추분 -> JP만 빠진다
2026-09-02(수)  14행  US JP HK CN GB        베트남 국경일 -> VN만 빠진다
```

**그런데 붙이지 않기로 했다.** 한 번 구현했다가 되돌렸다. 이유는 이득이 비용에 비해 작다는 것이다.

```
아끼는 호출    연간 약 1,000회 = 하루 3회
              (미국 9일 + 일본 17일, 10분 주기 x 장 운영시간)
드는 비용      1. 조회 범위가 당월 말까지다. 2026-09-12에 재보니 9/30까지는 정상이고
                 10/01부터 평일도 전부 0행이었다
              2. 그래서 0행이 "휴장"인지 "데이터 없음"인지 응답으로 구분되지 않는다.
                 0행을 휴장으로 믿으면 10월 1일에 해외 지표 갱신이 통째로 멈춘다
                 (실제로 그렇게 짰다가 발견해서 고쳤다)
```

KIS 호출 한도는 초당 기준이라 하루 3회는 의미가 없다. 애매한 계약을 가진 API를 하나 더 물고
조용히 멈출 위험을 안는 것보다, 해외 공휴일에 값 안 변하는 호출을 몇 번 더 하는 편이 낫다.

**해외 공휴일에 갱신을 시도해도 화면은 틀어지지 않는다.** KIS가 마지막 종가를 주므로 캐시 값이
그대로 유지된다. 낭비되는 것은 호출 횟수뿐이다.

나중에 호출량이 실제로 문제가 되면 위 API와 실측 결과를 그대로 쓰면 된다.
그때는 **0행을 휴장으로 해석하지 말 것** — 판정 불가로 두고 개장으로 기울여야 한다.

### 갱신 흐름

1. **서버가 켜질 때** (`backend/main.py`)
   - `market_indicator_service.refresh_all(force=True)`를 한 번 실행해서 캐시를 채워둔다(장이 닫혀있어도 무조건 한 번은 채움).
   - `APScheduler`로 10분마다(0/10/20/30/40/50분) `refresh_all()`을 자동으로 다시 실행하도록 예약해둔다.

2. **`refresh_all()`이 실행될 때** (`services/market_indicator_service.py`)
   - `_INDICATOR_DEFS`에 적힌 6개 지표를 하나씩 돈다.
   - 각 지표마다 `market_hours.is_market_open()`으로 시장이 열려있는지 확인한다.
     - 닫혀있으면 → 건너뛴다(캐시의 이전 값 유지 = 장마감 시 값 고정).
     - 열려있으면(달러환율은 항상) → `kis_client.py` 함수를 호출한다.

3. **`kis_client.py`가 KIS 서버에 요청** — `get_access_token()`으로 토큰을 준비(캐시된 토큰 재사용)한 뒤, 국내지수는 `get_domestic_index_price()`, 해외지수·환율은 `get_overseas_index_or_fx_price()` 호출

4. **데이터 가공** (`_refresh_one()`) — 응답에서 현재가·전일대비율만 뽑아 `_cache` 딕셔너리에 저장

5. **프론트 요청 시** (`routers/timeline.py`) — `GET /timeline/indicators`는 KIS를 다시 호출하지 않고 `_cache` 값을 스키마 형태로 변환해 응답

정리하면: **KIS 호출은 정시 스케줄러가 백그라운드에서만 하고, 프론트 요청은 항상 캐시된 값을 즉시 받아간다.**

> 프론트도 10분 주기에 맞춰 재요청해야 화면이 갱신된다. 브라우저 탭이 백그라운드이거나 절전 상태면 타이머가 밀릴 수 있음.

## 메인 콘텐츠 수집 — 동작 순서

수집·LLM 생성·DB 저장·조회·스케줄러까지 모두 붙어 있다.

### 엔드포인트

| 경로 | 내용 |
|---|---|
| `GET /timeline?date=` | **하루치 조회. 프런트가 쓰는 엔드포인트.** DB에서 읽어 즉시 응답(0.2초) |
| `POST /timeline/collect/{slot_key}` | 슬롯 하나를 수집해서 DB에 저장. 스케줄러가 부를 동작을 수동 실행 |
| `GET /timeline/indicators` | 최상단 지표 바 (캐시에서 읽음) |
| `GET /timeline/slots` | 호출 가능한 슬롯 목록 |
| `GET /timeline/glossary` | 용어 사전 `{용어: 설명}` 19개. 프런트가 호버 설명에 쓴다 |
| `GET /timeline/slot/{slot_key}` | DB를 거치지 않고 즉석 수집 (확인용) |

`GET /timeline`은 오늘 날짜를 조회하면 아직 시간이 안 된 슬롯을 빼고 준다. 지난 날짜는 전부 내려준다.
슬롯 시각에 수집을 시작하므로 데이터가 시각보다 먼저 생길 일은 없지만, 확인용으로 미래 슬롯을
수동 수집했을 때를 막는 안전망으로 남겨뒀다.

수집·저장에 걸리는 시간은 슬롯당 1~2분이다(실측 78초, LLM 3회 포함). `with_briefing=false`를 붙이면
LLM을 건너뛰어 1~2초에 끝난다.

`slot_key`는 콜론 없이 4자리로 받는다(`0730`, `1200`). URL에 콜론을 쓸 수 없어서다. DB에 저장할 때 쓰는 `07:30` 형태로는 서비스 안에서 변환한다. 시간대 정의(`_SLOT_DEFS`)와 명칭도 여기 있다.

슬롯별로 채워지는 항목이 다르다.

- 주도 섹터: 07:30 / 08:30은 빈 배열. 정규장 밖에는 업종 지수가 돌지 않는 것을 실측으로 확인했다
- 지표 6종: 07:30에만 채워진다. 그 시간에는 환율 빼고 전 시장이 닫혀 있어서 지수 5종은 어제 국내 종가와 밤사이 미국 마감값이고, 슬롯 성격("어제 마감 & 글로벌 현황")과 정확히 맞는다.
  **캐시를 읽지 않고 새로 받는다**(`force_refresh=True`). 환율은 24시간 움직여서 캐시가 최대 10분 낡을 수 있고, 지표 바 갱신이 07:30 정각에 같이 예약돼 있어 순서를 보장할 수 없다. 이 값이 15:30 장중 변화의 기준점이고 놓치면 되살릴 수 없다. 15:30 슬롯도 같은 이유로 새로 받으므로 두 시점을 같은 방식으로 잰다
- 브리핑·주린이 해설: LLM이 아직 없어서 응답 필드 자체를 넣지 않았다. 빈 배열로 자리만 두면 프런트가 오해할 수 있어서 LLM 붙일 때 필드째로 추가한다
- 장중 변화(15:30): 07:30 시점 값이 저장돼 있어야 만들 수 있어서 저장 로직이 붙은 뒤에 넣는다

### 단계별 소요 시간

수집 함수가 단계마다 걸린 시간을 찍는다(`timeline_service._timed`). 느려지거나 실패했을 때
KIS인지 네이버인지 제미나이인지 총시간만으로는 가릴 수 없어서 넣었다.

```
[수집] 07:30 시작
  [지표 6종] 0.5초
  [뉴스] 1.9초
  [LLM 브리핑·해설] 4.6초
[수집] 07:30 완료 - 총 7.1초
```

**측정값 해석에 주의할 것.** 위는 2026-09-12(토) 측정치로 뉴스가 6건뿐이었다.
거래일에는 뉴스가 30건 가까이 들어가 프롬프트가 몇 배로 길어지고, 그때 실측은 **78초**였다.
짧은 프롬프트로 잰 값을 그대로 믿으면 안 된다(전에 "30초→2초"로 잘못 판단한 적이 있다).

KIS·네이버 수집만 보면 슬롯당 1초 안팎이다(8슬롯 전체 0.5~1.4초). **병목은 전부 LLM이다.**

**주도 섹터** (`services/leading_sector_service.py`)

1. `collect()`가 `kis_client.get_index_category_price("K")`로 코스피 업종 전체를 받는다
2. `KOSPI_SECTOR_CODES`에 있는 업종만 남기고(38행 -> 21행) 등락률 내림차순으로 정렬한다
3. 상위 3개 각각에 대해 `get_fluctuation_ranking()`과 `get_volume_ranking()`을 호출해 1위 종목을 뽑는다
4. 두 API가 같은 종목을 가리키면 "상승·거래 1위"로 한 줄로 합치고, 다르면 "상승 1위" / "거래 1위" 두 줄로 만든다

지표 바와 달리 캐시를 두지 않았다. 슬롯을 만들 때 한 번만 필요한 값이라 조회한 결과를 바로 DB에 넣는 쪽이 맞기 때문이다.

**API 호출 실패 처리**

`kis_client.py`와 `naver_client.py`의 조회 함수는 실패하면 최대 3회까지 다시 시도한다(0.5초부터 조금씩 늘려가며 대기).

- 5xx와 연결 오류는 재시도한다. KIS는 초당 호출 한도를 넘기면 HTTP 500 + `EGW00201`을 주는데(확인 완료), 주도 섹터가 한 번에 7회를 연달아 부르기 때문에 여기 걸릴 수 있다
- 4xx는 요청이나 키가 잘못된 것이라 다시 보내도 결과가 같으므로 바로 에러를 낸다
- 토큰 발급(`get_access_token`)에는 재시도를 적용하지 않았다. 계좌 주인에게 알림이 여러 번 가기 때문이다

**뉴스** (`services/news_service.py`)

1. `collect(time_slot)`이 `_SLOT_KEYWORDS`에서 그 슬롯의 검색어를 꺼낸다
2. 검색어마다 `naver_client.search_news(sort="sim")`으로 30건씩 받는다
3. `<b>` 태그와 HTML 특수문자를 없애고, `pubDate`를 한국 시간 datetime으로 바꾼다
4. 링크 기준으로 합치면서 중요도 점수를 더한다(같은 기사가 여러 검색어에 걸리면 점수가 올라간다)
5. `_SLOT_WINDOW` 구간에 드는 기사만 남긴다. 3건 미만이면 구간을 6시간으로 넓혀 한 번 더 걸러본다
6. 점수 높은 순으로 상위 N건을 고른 뒤, 화면 순서는 최신순으로 되돌려 돌려준다

## LLM 연동 (브리핑·불개미 요약)

프롬프트 문구는 전부 `services/prompts.py`에 있다. 결과를 보면서 계속 손보게 되는 값이라
서비스 코드와 분리해뒀다.

### 두 단계로 부른다

1. **브리핑** — 수집 데이터 → 헤드라인 + 부제 + 포인트 3개
2. **불개미 요약** — 위 브리핑 → 같은 내용을 입문자용으로 다시 쓴 것 3개

순서가 중요하다. 각각 원본 데이터에서 따로 만들면 두 요약이 서로 다른 얘기를 할 수 있다.
2단계 입력이 원본이 아니라 1단계 결과이므로 새로운 사실이 끼어들 여지가 없다.

뉴스 선별도 LLM이 한다(`news_service`). 그래서 슬롯당 LLM 호출은 3회다.

### 모델 — gemini-3.5-flash-lite

`gemini-3.6-flash`에서 바꿨다. 이유는 한도 하나다.

- **무료 한도**: 3.6-flash는 하루 20회다(429 응답의 `GenerateRequestsPerDayPerProjectPerModel-FreeTier`).
  슬롯당 3회 x 8슬롯 = 24회라 한도를 넘어서, 실제로 09:30 이후 슬롯 브리핑이 통째로 비었다.
  Lite는 하루 200회다.
- **속도**: 짧은 프롬프트로 재보면 30초에서 2초로 줄지만, 실제 브리핑 프롬프트는 뉴스 30건이
  들어가서 훨씬 길다. 슬롯 하나를 끝까지 만드는 시간은 실측 78초로, 교체 전(72~99초)과 큰 차이가 없다.
  **속도는 교체 이유가 되지 못한다. 실제 이유는 한도다.**

한도는 모델별로 따로 잡힌다. 한 모델이 429가 나도 다른 모델은 쓸 수 있다.

Lite로도 한도가 부족하거나 품질이 안 나오면, LLM 호출 3회를 1회로 합치는 방법이 있다
(후보 뉴스를 주고 "고를 번호 + 브리핑 + 불개미 요약"을 한 응답으로 받는 방식, 하루 8회).
테이블 구조는 그대로 두고 호출 방식만 바뀐다. 지금은 보류.

### 프롬프트에서 신경 쓴 것

- **숫자를 지어내지 못하게 막았다.** 입력을 `[확정 수치]`(시세 API에서 받은 값)와 `[뉴스]`로 나눠서
  넘긴다. 유가·금·선물은 계좌 권한이 없어 시세로 못 가져오므로 뉴스에서만 나오는데,
  기사 발행 시각을 같이 주고 "지금 값인 것처럼 쓰지 말고 출처를 밝혀라"를 규칙으로 넣었다.
  실제 결과에서 `기사에 따르면 브렌트유가 배럴당 100달러를 넘어서며`처럼 나온다.
- **투자 권유를 금지했다.** 화면에 "최종 투자 결정과 책임은 투자자 본인에게 있습니다" 안내가 붙는데,
  그러려면 본문이 실제로 권유를 안 해야 한다.
- **문체를 못박았다.** 규칙이 없으면 모델 성향대로 나온다. 3.6-flash는 `~했습니다`체,
  Lite는 `~보였다`체로 썼다. 시안에 맞춰 `~습니다`체와 `%` 기호로 고정했다.
- **용어 풀이를 LLM에게 맡기지 않는다.** Lite가 `매도세`를 "판 것보다 산 것이 적은 상태"라고
  뒤집어 쓴 적이 있다(맞는 설명은 그 반대). 입문자용 해설에서 정의가 틀리면 그냥 둘 수 없어서
  19개 용어의 설명을 우리가 정해뒀다.
- **불개미 해설이 브리핑을 베끼지 못하게 했다.** "브리핑과 똑같은 문장이 나오면 잘못한 것"을
  규칙에 넣었다.

### 주린이 해설 — 용어 정의에서 문맥 설명으로 (2026-09-12)

처음에는 용어집을 프롬프트에 넣고 "이 용어가 나오면 괄호로 설명을 붙여라"라고 지시했다.
그랬더니 결과가 해설이 아니라 **용어 사전처럼** 나왔다. 세 문단에 괄호 설명이 대여섯 개 들어가면
정작 "왜 그런 일이 일어났는지"를 쓸 자리가 없다.

해설의 역할은 단어를 정의하는 게 아니라 문맥을 전달하는 것이다. 그래서 지시를 바꿨다.

- 전문 용어에 **괄호로 뜻을 붙이지 못하게 금지**했다
- 대신 그 용어를 몰라도 상황이 이해되게 문장을 쓰게 했다
  (`순매도가 이어졌습니다` -> `외국인이 계속 주식을 팔았습니다`)
- 나쁜 예를 두 개 넣었다. 브리핑을 그대로 옮긴 것, 단어만 정의한 것 둘 다 실패다

바뀐 결과(실측):

```
[국내 주가와 환율이 내린 이유]
국내 시장에서 주가가 내린 것은 투자자들이 안전한 현금을 선호하며 주식을 팔았기 때문입니다.
환율이 내린 것은 원화의 가치가 전날보다 조금 올랐음을 뜻합니다.
```

**용어 사전은 버리지 않고 `services/glossary.py`로 옮겼다.** LLM이 만든 정의가 아니라
우리가 검수한 19개라 그대로 쓸 수 있다. `GET /timeline/glossary`로 내려가고,
**프런트가 본문의 용어에 마우스를 올리면 설명이 뜨는 방식으로 처리한다.**
이렇게 하면 아는 사람은 그냥 읽고 모르는 사람만 확인하면 된다.

용어를 늘리거나 설명을 다듬으려면 `glossary.py`의 표만 고치면 된다.
주식 잘 아는 사람에게 검토받을 때 이 표를 같이 볼 것.

### 실패해도 슬롯이 죽지 않는다

LLM이 실패하면 경고만 찍고 나머지는 정상 저장된다.

- 뉴스 선별 실패 → 점수 상위 N건으로 대체
- 브리핑 실패 → `briefing_headline`이 `None`. 지표·뉴스·주도 섹터는 그대로 나간다
- 불개미 요약은 브리핑을 재료로 쓰므로, 브리핑이 없으면 빈 배열

결과를 눈으로 확인하려면 저장하지 않는 즉석 조회를 쓴다. **라이브 데이터를 건드리지 않는다.**

```
curl 'http://127.0.0.1:8000/timeline/slot/1200'
```

## DB 저장·조회

`services/timeline_repository.py`가 DB 접근을 전담한다. 조립(`timeline_service`)과 나눈 이유는
수집·가공 로직과 DB 접근이 한 파일에 섞이면 저장 방식만 바꾸고 싶을 때 건드릴 범위가 넓어지기 때문이다.

### 재실행 안전하게 만든 두 가지

**같은 슬롯을 다시 돌리면 덮어쓴다.** `trade_date` + `time_slot`에 유니크 제약이 있어서 그냥
INSERT하면 두 번째 실행부터 에러가 난다. 테스트 반복, 수집 실패 후 재시도, 서버 재시작 모두
재실행이 필요하다.

**새로 만든 게 비었으면 기존 값을 유지한다.** 브리핑이 잘 들어간 슬롯을 지표 때문에 다시 수집했다가
그 순간 LLM 한도에 걸려서 멀쩡했던 브리핑이 빈 값으로 덮인 일이 있었다. 지금은 새 브리핑이 없으면
기존 브리핑과 불개미 요약을 살려둔다.

### 비동기 ORM에서 주의할 점

조회할 때 `selectinload`로 자식 테이블을 미리 같이 읽어와야 한다. 동기 ORM처럼 나중에
`slot.news`를 꺼내려 하면 `MissingGreenlet` 에러가 난다. 테이블을 추가하면
`timeline_repository._EAGER_LOAD`에도 넣어야 한다. 빠뜨리면 그 값만 조용히 비어 보인다.

### 장중 변화 (15:30 슬롯)

그날 07:30 슬롯의 지표를 DB에서 읽어 현재 가격과 비교한다. 코스피·코스닥·환율 3종이고
명칭·07:30 가격·현재 가격·변동폭을 담는다.

07:30 슬롯이 없으면 경고를 찍고 빈 목록을 돌려준다. **07:30 시점의 환율은 지나가면 되살릴 수 없다**
(코스피·코스닥은 07:30 값이 곧 전일 종가라 복원 가능하지만 환율은 24시간 움직인다).
그래서 07:30 슬롯 수집이 실패하면 재시도로 반드시 채워두는 것이 중요하다.

## 결정된 설계 방향

### 테스트 데이터 지우기

```sql
DELETE FROM timeline_slot;   -- 자식 행이 전부 같이 지워진다
```

ORM 쪽 `cascade="all, delete-orphan"`과 DB 쪽 `ON DELETE CASCADE`를 둘 다 걸어뒀기 때문이다.
두 개를 같이 걸어둔 이유가 있다. `cascade`는 파이썬 코드로 지울 때(`session.delete`)만 동작한다.
Supabase 대시보드에서 SQL을 직접 실행하면 ORM을 거치지 않아서 FK 제약에 막혀
`ForeignKeyViolationError`가 났다.

id를 1번부터 다시 시작하려면 삭제 후 9개 테이블의 시퀀스를 각각 초기화한다.

```sql
ALTER SEQUENCE timeline_slot_id_seq RESTART WITH 1;
-- timeline_briefing_insight / timeline_beginner_guide / timeline_news / timeline_indicator
-- timeline_intraday_change / timeline_top_gainer
-- timeline_leading_sector / timeline_leading_sector_stock 도 동일하게
```

### 갱신 타이밍 — 타임라인 시각에 바로 반영한다

세시반을 관찰한 결과, 14:00이 되면 데이터는 바로 들어오지만 **새로고침을 해야 화면에 보인다.**
우리는 그렇게 하지 않고, 정해진 시각에 바로 저장하고 프런트에도 바로 뿌리는 방향으로 간다.

여기서 갈리는 지점이 하나 있다. 백엔드가 제때 저장해도 **브라우저가 다시 요청하지 않으면 화면은 그대로다.**
"새로고침 없이 바로"를 만들려면 프런트 쪽 방식을 정해야 한다.

- 폴링: 프런트가 슬롯 시각에 맞춰 다시 요청한다. 만들기 쉽지만 탭이 백그라운드면 타이머가 밀릴 수 있다
- 서버 푸시(SSE/WebSocket): 백엔드가 저장 직후 프런트로 밀어준다. 정확하지만 구현이 늘어난다

지표 바도 같은 문제를 안고 있다(10분 갱신). 프런트 담당자와 같이 정할 것.

### 스케줄러 수집 시각

슬롯 시각이 되면 그때 수집한다. 생성에 1~2분 걸리므로(실측 78초) 화면에는 그만큼 늦게 뜬다.

**여덟 슬롯 모두 슬롯 시각 정시에 수집한다.** 예외는 없다.

| 슬롯 | 07:30 | 08:30 | 09:30 | 12:00 | 14:00 | 15:30 | 17:30 | 20:00 |
|---|---|---|---|---|---|---|---|---|
| 수집 | 07:30 | 08:30 | 09:30 | 12:00 | 14:00 | 15:30 | 17:30 | 20:00 |

### 15:30 슬롯 — 정시로 통일했다 (2026-09-12)

전에는 15:35였다. 코스피 종가가 15:20~15:30 마감 동시호가로 정해지므로 정시에 조회하면
마감 전 값이 들어갈 수 있다는 우려였다. 정시로 바꾼 이유는 두 가지다.

1. **그 차이가 실제로 있는지 확인된 적이 없다.** 소급 조회가 불가능해서 재볼 수도 없었다
   (지수 시간별 조회는 지금부터 거슬러 최근 100틱만 주고, 과거 시각을 넣으면 무시된다.
   휴장일에 호출하면 0행이 온다). 확인되지 않은 우려 때문에 슬롯 하나만 규칙을 다르게
   유지하는 대가가 더 컸다.
2. **캐시 문제를 이미 고쳤다.** 예전에는 장중 변화가 지표 *캐시*를 읽었는데, 캐시는 10분
   주기로 갱신되고 15:40에는 장마감이라 건너뛴다. 그래서 15:35에 만들어도 캐시에는
   15:30:00 값이 있었다 — **5분을 기다린 효과가 애초에 없었다.** 지금은 이 슬롯만
   `_indicator_rows(force_refresh=True)`로 새로 받는다.

**월요일(9/14) 실데이터에서 확인할 것.** 15:30 슬롯의 `closing_price`와 실제 종가를 비교한다.
다르면 `SLOT_COLLECT_TIMES`의 `"1530"`만 `(15, 35)`로 되돌리면 된다.

처음에는 **5분 전에 미리 만들어두는 방식**이었는데 바꿨다. 정각에 화면에 띄우려던 의도였지만
근거가 약했다.

- 데이터가 슬롯 시각과 어긋난다. "12:00 오전장 흐름"에 11:55 값이 들어간다. 화면 노출은
  지나가면 끝이지만 **저장된 데이터는 영구히 남는다.**
- 뉴스 구간이 잘린다. 12:00 슬롯의 구간은 09:30~12:00인데 11:55에 수집하면 마지막 5분이 빠진다.
- 07:30 환율이 실제로는 07:25 값이 되어, 15:30 장중 변화가 그 값을 기준으로 계산된다.
- 미리 만드는 방식은 **마감이 있다.** 07:25에 실패하면 07:30까지 5분 안에 성공해야 한다.
  정시 수집은 마감이 없어서 실패해도 다시 시도하고 조금 늦게 올리면 된다.
- 15:30을 이미 정확성 때문에 뒤로 미뤄뒀는데, 나머지 7개만 정각 노출을 우선하는 건 앞뒤가 안 맞았다.

대가는 슬롯이 1~3분 늦게 뜬다는 것인데, 하루 8번 갱신되는 타임라인에서 정각 노출은 아무도
체감하지 못한다. 레퍼런스인 세시반도 새로고침해야 보인다.

시각을 바꾸려면 `timeline_service.SLOT_COLLECT_TIMES` 표만 고치면 된다.

### 프런트는 어떻게 데이터가 준비된 걸 아는가

별도 확인 방법이 필요 없다. `GET /timeline`이 **DB에 있는 슬롯만** 배열로 주기 때문이다.

```
09:35에 요청 -> [07:30, 08:30, 09:30]        3개
12:00에 요청 -> [07:30, 08:30, 09:30]        3개  (12:00은 아직 생성 중)
12:03에 요청 -> [07:30, 08:30, 09:30, 12:00] 4개
```

프런트는 주기적으로(1분 정도) 다시 부르고, 배열에 새 슬롯이 생겼으면 화면에 붙이면 된다.
DB에서 읽기만 해서 0.2초에 응답하므로 1분 폴링은 부담이 없다.

"생성 중"을 화면에 표시하고 싶으면 프런트에서 구분할 수 있다. `GET /timeline/slots`로 받은
슬롯 시각이 지났는데 `GET /timeline` 응답에 없으면 생성 중이다. 백엔드 수정은 필요 없다.

나중에 폴링이 마음에 안 들면 SSE로 올릴 수 있다. 폴링으로 시작하고 필요할 때 바꾼다.

### 휴장일에는 아무것도 하지 않는다 (실측 확인)

주말과 공휴일에는 슬롯을 만들지 않는다. 레퍼런스인 세시반도 그날은 데이터를 제공하지 않는다.

판단은 국내휴장일 조회(`CTCA0903R`)를 쓴다. 응답의 `opnd_yn` 한 필드로 주말이든 공휴일이든
장이 안 서는 날이 전부 `N`으로 온다. 우리가 요일을 따지거나 공휴일 목록을 관리할 필요가 없고,
임시공휴일·대체공휴일도 거래소가 반영한 대로 따라간다. 한 번에 20여 일치가 오므로
`market_hours._open_day_cache`에 담아 재사용한다.

```
9/11(금) O   9/12(토) X   9/13(일) X   9/14(월) O
9/24(목) X   9/25(금) X   9/28(월) O        <- 추석도 정상 감지
```

**어디까지 막는가** — 호출 단위로 세어 확인했다.

| 대상 | 장마감 | 국내 휴장일 | 해외 휴장일 | 주말 |
|---|---|---|---|---|
| 코스피·코스닥 | 호출 X | **호출 X** | (해당 없음) | 호출 X |
| 니케이·나스닥·S&P500 | 호출 X | 호출 O | 호출 O (한계) | 호출 X |
| 환율 | 항상 호출 | 항상 호출 | 항상 호출 | 항상 호출 |
| 타임라인 슬롯 | — | **전부 호출 X** | (국내 기준만 봄) | 전부 호출 X |

```
지표 바 (10분 주기)                   실제 호출된 지표
  금 10:00  국장 중          코스피, 코스닥, 환율, 니케이     4회
  금 17:00  국장 마감 후      환율                        1회
  금 23:30  미장 중          나스닥, S&P500, 환율          3회
  추석(목) 10:00  국장 휴장   환율, 니케이                  2회   <- 국내만 빠진다
  토 10:00  주말            환율                        1회

타임라인 슬롯 (휴장일에 8슬롯 전부 호출해봄)
  KIS 0회 / 네이버 0회 / 제미나이 0회      <- 외부 호출이 아예 없다
```

슬롯 수집은 `is_trading_day()` 확인이 **KIS·네이버·제미나이 호출과 DB 접근보다 앞**에 있어서
휴장일에는 수집 자체가 시작되지 않는다.

**조회에 실패하면 개장일로 본다.** 휴장일에 괜히 수집하는 건 데이터를 지우면 되지만, 개장일인데
건너뛰면 그 슬롯을 영영 못 채운다. 특히 07:30 환율은 그 시점을 놓치면 되살릴 방법이 없다.

예외가 하나 있다. **서버가 켜질 때는 `refresh_all(force=True)`로 6종을 무조건 한 번 채운다.**
캐시가 비면 지표 바가 아무것도 못 내려주기 때문이다(장이 닫혀 있어도 마지막 종가는 보여줘야 한다).

### AsyncIOScheduler를 쓴다

`BackgroundScheduler`에서 바꿨다. 슬롯 수집 함수가 `async def`인데, `BackgroundScheduler`는 별도
스레드에서 돌아서 비동기 함수를 실행할 수 없다. **등록해두면 에러도 안 나고 아무 일도 안 일어난다.**
로그에는 작업을 실행했다고 찍히는데 DB에는 아무것도 없는 상태가 된다.

`AsyncIOScheduler`는 FastAPI가 이미 돌리고 있는 이벤트 루프 위에서 돌아 `async` 함수를 제대로
실행한다. 평범한 함수(지표 바 갱신)도 그대로 받아준다.

주의: 이벤트 루프가 있어야 도므로 **서버를 띄웠을 때만 동작한다.** 스크립트로 따로 실행하면 안 돈다.

등록되는 작업은 9개다(지표 바 1 + 슬롯 8). `DATABASE_URL`이 없으면 슬롯 작업은 등록하지 않고
경고만 남긴다. KIS 키가 없으면 지표 바 작업을 등록하지 않는다.

`misfire_grace_time`을 10초로 뒀다. 기본값 1초는 너무 빡빡해서 서버가 잠깐 버벅이기만 해도
그 슬롯이 통째로 날아간다. 반대로 길게 잡으면 안 된다. 맥이 잠들었다 몇 시간 뒤에 깨어났을 때
07:30 슬롯이 09시에 뒤늦게 실행되면 그때 환율이 "07:30 가격"으로 저장되어 장중 변화가 틀어진다.
**없는 것보다 틀린 게 나쁘다.**

서버를 밤새 켜두려면 맥이 잠들지 않아야 한다. `caffeinate -d uv run fastapi run main.py`로
띄우면 서버가 도는 동안만 잠자기가 막힌다. `fastapi dev`는 파일이 바뀌면 서버를 재시작하므로
장시간 운영에는 `run`이 안전하다.

### 오류 로깅 (2026-09-12 구현)

**`print`를 전부 `logging`으로 바꿨다(16곳).** 설정은 `core/logging_config.py`에 있다.

바꾼 이유는 하나다. **print는 터미널에만 남아서 서버를 닫으면 사라진다.**
2026-09-11에 슬롯 3개가 저장 직전에 실패했는데 터미널이 이미 지나가서 원인을 찾는 데 한참 걸렸다.
실데이터를 쌓기 시작하면 아침에 일어나서 "07:30이 왜 비었는지"를 물어야 하는데, 그때 볼 게 있어야 한다.

**어디에 남는가**

```
1. 터미널                      전에 print로 보던 것과 같다
2. backend/logs/timeline.log   자정에 날짜를 붙여 넘기고 14일치 보관
                               (timeline.log.2026-09-14 형태)
```

`logs/`는 루트 `.gitignore`에 넣었다.

**레벨 기준**

| 레벨 | 언제 | 예 |
|---|---|---|
| INFO | 정상 흐름 | 수집 시작·완료, 단계별 소요 시간, 휴장일 건너뜀, 기존 브리핑 유지 |
| WARNING | 일부 실패했지만 슬롯은 만들어짐 | LLM 실패, 뉴스 선별 실패, 휴장일 조회 실패, 07:30 없어서 장중 변화 못 만듦 |
| ERROR | 슬롯이 통째로 실패 | 수집 실패. `exc_info=True`로 스택까지 남긴다 |

운영 중에는 이 한 줄만 보면 된다.

```
grep -E "WARNING|ERROR" logs/timeline.log
```

**외부 로거는 조용하게 낮췄다.**

```
httpx / httpcore   요청마다 INFO 한 줄. 슬롯 하나에 수십 번 부른다
apscheduler        작업 등록마다 두 줄. 작업이 9개라 서버를 켤 때마다 18줄
                   (실측: 낮추기 전 23줄 중 19줄이 이것이었다 -> 3줄로 줄었다)
```

둘 다 **WARNING 이상은 남겨뒀다.** 특히 apscheduler의 경고는 꼭 봐야 한다 —
예약 시각을 놓쳤을 때(`Run time of job ... was missed by ...`) 여기 찍힌다.
`misfire_grace_time`이 10초라 맥이 잠들었다 깨면 이 경고가 뜬다.

**시각은 한국 시간으로 못박았다.** 기본값은 기기의 지역 시간인데, 지금은 맥이 한국 시간이라
그대로도 맞지만 다른 환경에서 돌리면 로그 시각과 DB의 `time_slot`이 어긋난다.
이 프로젝트는 시간대 불일치로 이미 여러 번 헤맸다.

**쓰는 법** — 파일 맨 위에서 logger를 하나 만들고 `print` 대신 부른다.

```python
logger = logging.getLogger(__name__)
logger.warning("브리핑 생성 실패 - %s: %s", type(error).__name__, error)
```

f-string 대신 `%s`로 넘긴다. 그 레벨이 꺼져 있으면 문자열을 만드는 비용조차 들지 않는다.

남은 것: API 서버가 계속 꺼져 있어 데이터를 아예 못 가져오는 경우는 여전히 슬롯이 빈다.
일시적 실패는 재시도로 처리했지만(위 'API 호출 실패 처리' 참고) 지속적인 장애는 재시도로
해결되지 않는다. 지금은 ERROR 로그를 남기고 그 슬롯을 포기한다(다른 슬롯 예약은 살아 있다).

## 겪은 문제와 해결

같은 실수를 반복하지 않기 위해 남긴다. 날짜는 발견한 날이다.

| 문제 | 원인 | 해결 |
|---|---|---|
| 모델 파일 import 자체가 실패 | `__table_args__`에 `UniqueConstraint`를 튜플로 감싸지 않음 | 뒤에 콤마를 붙여 튜플로 만듦. 제약이 하나여도 필요하다 |
| `DATABASE_URL` 없으면 앱 기동 불가 | `database.py`가 import 시점에 엔진 생성 | `get_engine()` 함수로 감싸 처음 쓸 때 생성 |
| SQL 로그가 터미널을 뒤덮음 | `echo=True` | 껐음. 쿼리를 볼 필요가 있을 때만 켠다 |
| SQL로 슬롯을 지우면 FK 제약에 막힘 | `cascade`는 ORM으로 지울 때만 동작 | 모델·DB 양쪽에 `ON DELETE CASCADE` 추가 |
| 07:30 지표가 조용히 비어 저장됨 | 지표 캐시가 서버 기동 시에만 채워짐. 스크립트로 실행하면 빈 상태 | 캐시가 비면 `_indicator_rows()`가 먼저 채운다 |
| 재수집 시 기존 브리핑 유실 | 덮어쓰기가 새 값의 성공 여부를 안 봄 | 새 값이 없으면 기존 값 유지 |
| 슬롯끼리 뉴스가 10건 중 9건 겹침 | 모든 슬롯이 "최근 24시간" 창을 씀 | 직전 슬롯 이후 구간으로 나눔 |
| 07:30의 중요한 밤 기사가 잘려나감 | 최신순으로 자름 | 중요도 점수순으로 고르고 표시 순서만 최신순 |
| 불개미 해설의 용어 정의가 틀림 | LLM이 설명을 창작(`매도세`를 반대로 씀) | 용어 19개를 우리가 정해뒀다. 처음엔 프롬프트에 넣었고, 지금은 `glossary.py`로 옮겨 프런트 호버용으로 쓴다(아래 항목 참고) |
| LLM 브리핑이 뒤쪽 슬롯부터 통째로 빔 | 제미나이 무료 한도 하루 20회 초과 | 모델을 Lite(하루 200회)로 교체 |
| 제미나이 타임아웃에 슬롯 생성이 통째로 죽음 | `httpx` 예외를 안 잡고 있었음 | `llm_client`에 재시도 추가, `httpx.HTTPError`까지 방어 |
| 슬롯 생성 속도를 10초로 잘못 판단 | 짧은 프롬프트로만 측정함. 실제 프롬프트는 뉴스 30건이 들어가 훨씬 길다 | 실측 78초로 정정 |
| `llm_client`에 재시도를 넣었다고 착각 | 상수와 주석만 들어가고 함수 본문이 안 바뀜. 다른 곳의 예외 처리가 넓어져서 증상이 가려졌다 | 전체 점검에서 발견해 실제로 적용. **주석이 코드와 다를 수 있으니 동작으로 확인할 것** |
| 지수 시간별 조회에서 `99:99:99` 응답 | 체결 없는 자리를 더미 값으로 채워서 보냄(분봉의 `88:88`과 같은 현상) | 시(hour) 자리가 00~23이 아닌 행을 걸러냄 |
| 응답의 `code` 필드가 DB 경로에서 항상 빈 값 | 업종코드·지표코드를 테이블에 저장하지 않음 | 스키마에서 제거. 항상 비는 필드는 두지 않는다 |
| 슬롯 3개가 저장 직전에 전부 실패(NOT NULL 위반) | `created_at`을 파이썬에서 넣도록 바꾸면서 DB 기본값을 지웠는데, **돌고 있던 서버는 옛날 코드**라 값을 안 보냈다. `fastapi run`은 자동 재시작이 없어서 코드를 고쳐도 서버는 예전 상태였다 | DB에도 `DEFAULT (now() AT TIME ZONE 'Asia/Seoul')`을 안전망으로 걸었다. **스키마를 바꾸면 서버를 반드시 재시작할 것** |
| 애프터마켓 데이터가 없다고 잘못 보고 | KRX 시간외단일가(거래 거의 없음)만 보고 NXT 애프터마켓(활발함)을 확인 안 함. `NX` 코드는 문서에 있었는데 정규장 중에만 테스트했다 | 시장구분 파라미터는 **그 값이 유효한 시간대에** 다시 호출해볼 것 |
| 급상승 TOP3가 브리핑에 반영되지 않음 | `briefing_service._build_data`가 지표·주도 섹터·뉴스만 받았다. 08:30 / 17:30 / 20:00은 주도 섹터도 지표도 비어서 **확정 수치가 통째로 없는 상태로 뉴스만 보고 브리핑을 쓰고 있었다** | `top_gainers`를 입력에 추가. 빈 항목은 아예 넘기지 않게 해서 LLM이 "데이터 없음"에 끌려가지 않게 했다 |
| 장 마감 슬롯을 15:35로 미뤘는데 효과가 없었음 | 장중 변화가 지표 **캐시**를 읽었다. 캐시는 10분 주기라 15:35에는 15:30 값이 들어 있었다. 5분을 기다린 의미가 사라진 상태 | `force_refresh=True`로 새로 받게 했다. 그 뒤 수집 시각도 15:30 정시로 통일했다 |
| KIS 장애 시 서버가 아예 안 뜸 | `main.py`가 `RuntimeError`만 잡음. 타임아웃은 `httpx` 예외라 lifespan 밖으로 나가 기동 실패 | `except Exception`으로 넓혔다. 지표 바만 끄고 앱은 띄운다 |
| 브라우저에서 수동 수집 불가 | CORS `allow_methods=["GET"]`인데 `POST /timeline/collect`가 있다. curl은 CORS를 안 봐서 안 드러났다 | `POST` 추가 |
| 주린이 해설이 용어 사전처럼 읽힘 | 프롬프트가 용어마다 괄호 설명을 붙이게 지시 | 괄호 설명을 금지하고 문맥 설명으로 전환. 용어집은 `glossary.py`로 옮겨 프런트 호버용으로 넘김 |
| `prompts.py`가 옛 버전으로 되돌아가 있었음 | 편집기에 열려 있던 옛 버전이 저장되며 덮인 것으로 보임. `GLOSSARY_TEXT`가 지워졌는데 `briefing_service`는 계속 참조해서 **`AttributeError`로 슬롯 전체가 저장 실패하는 상태**였다. 그 예외는 `except` 목록에 없어서 위로 그대로 올라간다 | `git checkout HEAD --`로 복구 후 다시 작업. **작업 시작 전에 `git status`를 먼저 볼 것** |
| 틀린 주석 다수 | 기능이 바뀌었는데 주석을 안 고쳤다. "아직 DB에 저장하지 않는다", "정시(00분/30분)마다", "published_at은 DB에 저장하지 않는다" 등 | 전부 수정. **주석이 코드와 다를 수 있으니 동작으로 확인할 것**(같은 교훈 두 번째다) |
| 슬롯 시각 정각 기사가 두 슬롯에 중복 | 뉴스 구간을 `시작 <= 발행 <= 끝` 양쪽 포함으로 잡았다. 08:30:00 기사가 08:30 슬롯과 09:30 슬롯에 둘 다 들어간다 | 끝을 배타적으로(`< 끝`) 바꿨다. `[20:00, 07:30)` `[07:30, 08:30)`처럼 빈틈도 겹침도 없다 |
| 15:30 브리핑이 장중 변화를 못 봄 | 장중 변화를 수집·브리핑이 **끝난 뒤에** 계산했다. "장 마감" 브리핑이 그날 시장이 얼마나 움직였는지를 모르고 뉴스·섹터만 보고 글을 썼다 | 순서를 바꿔 브리핑보다 먼저 만든다 |
| 급상승 TOP3 순서가 등락률 순이 아님 | NX 응답의 `data_rank`가 `prdy_ctrt`와 다른 기준으로 매겨져 있다(1위 영풍 +26.40% / 2위 에스투더블유 +29.96%). 거래소(J)는 정상 | 30행을 받아 등락률로 직접 정렬한 뒤 상위 3개를 쓴다. **화면에 보여주는 숫자로 정렬할 것** |
| 08:30 슬롯 이름과 데이터 출처가 어긋남 | 슬롯 이름은 "NXT 프리마켓"인데 KRX 장전 예상체결을 썼다. 게다가 KRX 동시호가는 08:30에 시작해서 정각 조회 시 비어 있을 수 있다 | 세 슬롯 모두 NXT로 통일. 예상체결 함수는 대체 수단으로 남겨뒀다 |
| 07:30 지표가 10분 낡을 수 있었음 | 캐시를 읽는데 지표 바 갱신이 07:30 정각에 같이 예약돼 있어 순서를 보장할 수 없다. 지수 5종은 시장이 닫혀 같은 값이지만 **환율은 24시간 움직인다** | 이 슬롯도 `force_refresh=True`. 15:30 장중 변화의 기준점이고 놓치면 되살릴 수 없다 |
| 서버를 닫으면 실패 원인이 사라짐 | 전부 `print`였다. 슬롯 3개가 날아간 원인을 찾는 데 한참 걸렸다 | `logging`으로 전환(16곳) + 파일 보관. 레벨·스택·KST 시각이 남는다 |
| 로그가 apscheduler 잡음에 묻힘 | 작업 등록마다 두 줄씩 INFO를 남긴다. 작업이 9개라 기동 로그 23줄 중 19줄이 그것이었다 | `apscheduler`/`httpx`를 WARNING으로 낮췄다(23줄 -> 3줄). 경고·오류는 남겨둔다 |

반복해서 물린 것 두 가지는 따로 적어둔다.

1. **주석이 코드와 다를 수 있다.** `llm_client`에 재시도를 넣었다고 착각한 일(상수와 주석만 들어가고
   함수 본문이 안 바뀜), 기능이 바뀐 뒤 주석을 안 고친 일이 여러 번 있었다. **동작으로 확인할 것.**
2. **스키마나 코드를 바꾸면 서버를 재시작해야 한다.** `fastapi run`은 자동 재시작이 없다.
   돌고 있는 서버가 옛 코드라서 슬롯 3개가 통째로 실패한 일이 있었다.

## 팀 협업 규칙 (2026-09-10 기준)

1. `core` 폴더는 전역으로 모든 작업자가 사용
2. API 호출 파일은 `(api명)_client.py` 형식으로 작성 (예: `kis_client.py`)
3. 같은 API라도 함수마다 가져오는 데이터가 다르므로 각 함수 위에 주석으로 명시
4. **`core`를 수정하더라도 main에 바로 올리지 않고 본인 브랜치에서 작업한다. 최종적으로 브랜치를 합칠 때 함께 병합한다.**
   - 초기에는 "core만 main에 먼저 push하고 각자 받아가는" 방식이었으나, 브랜치별로 작업하다 마지막에 합치는 방식으로 변경됨
   - 대신 병합 시점에 `config.py`처럼 여러 명이 같이 건드리는 파일에서 충돌이 날 수 있으니, 합치기 전에 서로 어떤 파일을 건드렸는지 공유할 것
5. 병합 전에는 서버를 띄워 동작 확인 (`uv run fastapi dev main.py`)
6. `.env`는 git에 올라가지 않으므로 수정 시 각 담당자에게 재전달

**병합 시 공유할 것 (timeline 브랜치가 건드린 `core`)**

| 파일 | 내용 |
|---|---|
| `core/logging_config.py` | **새로 추가.** 로그 설정. 각 파일에서 `logger = logging.getLogger(__name__)`로 쓰면 된다. `setup_logging()`은 `main.py` lifespan에서 이미 부른다 |
| `core/database.py` | **사용법이 바뀜.** `engine` 직접 참조 -> `get_engine()` / `get_session_factory()` |
| `core/kis_client.py` | 함수 추가(업종·종목순위·휴장일·예상체결), 재시도·토큰 캐시 |
| `core/naver_client.py` | 새로 추가. 네이버 뉴스 검색 |
| `core/llm_client.py` | 새로 추가. 제미나이 (모델 `gemini-3.5-flash-lite`) |
| `core/config.py` | 키 필드 추가. **여러 명이 같이 건드리는 파일이라 충돌 주의** |

Supabase 테이블 9개도 이 브랜치에서 만들었다. `created_at`은 전 테이블 한국 시간이다.

   - **KIS 토큰 캐시가 로컬 파일이다**(`.cache/kis_token.json`, 유효 24시간). 컨테이너
     파일시스템은 재배포마다 초기화되므로 그때마다 토큰이 재발급되고 **계좌 주인에게 알림이 간다.**
     DB 테이블로 옮기면 해결된다(Postgres가 이미 있다)
   - **무료 티어가 앱을 잠재우면 스케줄러가 죽는다.** 하루 8번 예약 수집이 서비스의 핵심인데
     무접속 시 spin down되면 슬롯이 안 쌓인다. 항상 켜진 티어를 쓰거나, 외부 cron이
     `POST /timeline/collect/{slot}`을 때리는 방식으로 바꿔야 한다(그러면 APScheduler를 빼도 된다).
     단 그 엔드포인트는 지금 인증이 없어서 아무나 수집을 트리거할 수 있다 — 막아야 한다
   - **인스턴스가 2개 이상이면 수집이 중복된다.** 데이터는 안 깨지지만 제미나이 호출이 2배가 된다
