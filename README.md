# 개미굴(Gaemigul)

> ※ 본 문서는 팀이 작성한 최초 기획 초안을 바탕으로, 이후 실제 구현된 코드베이스를 확인해 구현 현황을 반영한 버전입니다. 초안과 달라진 부분은 각 절 끝에 **[구현 현황]**으로 표시했습니다.

## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 프로젝트 주제 | 금융 뉴스 요약 및 시황 AI 인사이트 대시보드 (개미굴 / Gaemigul) |
| 해결하려는 문제 | 개인 투자자가 시세·뉴스·일정을 각각 다른 곳에서 확인하며 스스로 맥락을 재구성해야 하는 정보 파편화 문제 |
| 대상 도메인 및 데이터 | 국내 상장 주식(한정) + 해외 주요 지수·환율·금융 뉴스 |
| 사용 LLM API 또는 모델 | 미정 — 팀이 API를 지급받는 대로 연동 예정. 현재는 규칙 기반(통계 이상치 탐지 + 감성 키워드 사전) 로직으로 인사이트를 생성 중이며, LLM 연동 시 문장 생성부만 교체 가능하도록 설계 (3.7절 참고) |
| 주요 사용자·시나리오 | 주식을 시작한 지 얼마 안 된 투자자가 하루 중 정해진 시간대에 대시보드를 확인해 시황·뉴스·일정을 한 화면에서 파악 |

### 1.1 배경 및 목적

- 기존 주제였던 "채용공고 트렌드 대시보드"에서 "금융 뉴스 요약 및 시황 AI 인사이트 대시보드"로 주제를 전환함
- 전환 사유: 상업 목적이 아니더라도 크롤링을 통해 수집한 데이터를 정제 후 활용하는 방식이 포트폴리오용 프로젝트로 적합하지 않다고 판단
- 서비스 목표: **주식 입문자**도 국내외 시황과 관련 뉴스를 한눈에 파악하고, AI가 종합한 인사이트를 통해 시장 흐름을 쉽게 이해할 수 있도록 지원

### 1.2 데이터 범위

- **주식**: 국내 주식으로 한정
- **지표(지수) 및 금융 뉴스**: 해외 포함

### 1.3 핵심 컨셉

- 주식 입문자를 위해 전문 용어나 이해하기 어려운 내용은 강조 표시 후, 호버(hover) 시 설명을 제공

**[구현 현황]** `components/term.tsx` + `lib/glossary.ts`로 구현 완료

## 3. 시스템 아키텍처

### 3.1 전체 데이터 흐름

[외부 API/데이터 소스]
├─ 한국투자증권 API (국내 주식 시세) — 앱키 발급 전, 야후 파이낸스로 폴백
├─ finlight (금융 뉴스) — 연동 예정, 현재는 언론사 RSS로 대체
├─ 네이버 뉴스 Search API (종목/섹터 뉴스) — 어댑터 구현, 키 발급 전
└─ FRED 증시 API (증시 일정/발표) — 연동 예정, 현재는 조사된 확정 일정(FOMC/금통위)으로 시딩
│
▼
[데이터 수집·정제 계층] domain/*/services (collector, sentiment, indicator_collector 등)
│
▼
[RDB 적재 (SQLAlchemy ORM, 기본 SQLite / Supabase 연동 예정)]
│
▼
[FastAPI 백엔드]
├─ 도메인별 API 라우터 (timeline, calendar, heatmap, news, insights)
└─ 규칙 기반 인사이트 생성 로직 (LLM API 연동 시 문장 생성부만 교체 가능한 구조)
│
▼
[대시보드 (프론트엔드)]
메인 페이지 / 캘린더 페이지 / 히트맵 페이지

**[구현 현황]** 증시 일정 API는 FRED로 확정. 각 외부 소스는 "실 API 우선 시도 → 실패 시 자동 폴백" 구조로 구현되어, API 키가 없어도 항상 동작합니다.

### 3.2 요청 흐름 설명

메인 페이지(시황 타임라인) 기준으로, 사용자가 데이터를 확인하기까지의 흐름은 다음과 같습니다.

1. 사용자가 대시보드 메인 페이지(`/`)에 접속합니다.
2. 프론트엔드가 `GET /timeline/indicators`(헤더 지표)와 `GET /timeline`(당일 시황 타임라인)을 호출합니다.
3. 백엔드가 오늘 날짜 데이터를 조회합니다. 데이터가 하나도 없으면(최초 실행 등) 수집 파이프라인이 자동으로 1회 실행되어 먼저 채웁니다.
4. 조회된 원시 데이터는 인사이트 생성 로직(`insights/services/generator.py`, `timeline/services/report_generator.py`)을 거쳐 사람이 읽을 수 있는 문장으로 가공됩니다. 지금은 규칙 기반이며, LLM API 연동 시 이 단계만 교체됩니다.
5. 백엔드가 가공된 결과를 JSON으로 반환합니다.
6. 프론트엔드가 응답을 헤더 지표 바와 시황 타임라인 카드에 렌더링합니다.
7. 사용자가 특정 시점 카드를 클릭하면, 이미 받아온 응답 중 해당 시점 데이터를 화면에 표시합니다(추가 API 호출 없음).

캘린더(`GET /calendar`)·히트맵(`GET /heatmap`) 화면도 "조회 → (필요 시 자동 수집) → 가공 → JSON 응답 → 렌더링"의 동일한 패턴을 따릅니다.

**[구현 현황]** 초안에는 없던 절로, 실제 구현 이후 서비스 흐름을 명확히 하기 위해 추가했습니다.

### 3.3 기술 스택

**백엔드**

- **프레임워크**: FastAPI (uv 패키지 매니저)
- **DB**: 기본 SQLite(로컬/데모), Supabase(PostgreSQL) 연동 예정 — `DATABASE_URL` 한 값만 바꾸면 전환되도록 설계
- **ORM**: SQLAlchemy 2.x
- **스케줄러**: APScheduler (주기적 데이터 수집)

**프런트엔드**

- **프레임워크**: Next.js (App Router)
- **스타일링**: Tailwind CSS + shadcn/ui, 아이콘은 lucide 사용

**[구현 현황]** 초안 대비 ORM(SQLAlchemy)과 스케줄러(APScheduler)가 실제 구현에서 확정되었습니다. DB는 아직 Supabase 연동 전이며 기본값은 SQLite입니다.

### 3.5 협업 및 Push 규칙

`core/` 폴더는 전역으로 모든 작업자가 공유하므로, 아래 규칙을 따릅니다.

1. **`core/` 폴더 역할** — 모든 도메인이 공유하는 코드가 위치합니다. `config.py`는 `.env` 파일에서 API 키를 일괄 호출하고, `database.py`는 DB 연동(세션·연결)을 전담합니다.
2. **API 클라이언트 파일명 규칙** — 외부 API를 호출하는 파일은 `(api명)_client.py` 형식으로 작성합니다. (예: 한국투자증권 API → `kis_client.py`)
3. **함수 단위 주석 규칙** — 함수마다 어떤 데이터를 조회하는지 주석으로 명시합니다. (예: `# 국내 지수(코스피/코스닥) 현재가 조회`)
4. **`core/` 수정 시 push 규칙** — 기존 코드를 수정·삭제하는 경우 팀에 공지 후 `main`에 push, 추가만 하는 경우 공지 없이 push. 수정 후 push 전에는 반드시 `uv run fastapi dev main.py`로 서버를 한 번 띄워 정상 동작을 확인합니다.
5. **일반 작업 규칙** — 본인 브랜치에서 작업 후 push. 작업 시작 전 `git pull origin main`으로 최신 변경 사항을 받아옵니다.
6. **`.env` 관리** — 변동 사항은 담당자에게 개별 전달하며 저장소에는 커밋하지 않습니다.

**[구현 현황]** 초안에는 없던 절로, 실제 협업 과정에서 확정된 팀 규칙을 정리했습니다.

### 3.6 API 명세

| Method | Endpoint | 설명 |
|---|---|---|
| GET | `/timeline/indicators` | 헤더 지표 바 데이터 조회 (KOSPI, KOSDAQ, NIKKEI, USD/KRW, S&P500, NASDAQ) |
| GET | `/timeline/indicators/{symbol}/history` | 지표 일별 히스토리 |
| GET | `/timeline` | 당일 07:30/09:00/12:00/15:30 시황 타임라인 |
| GET | `/timeline/reports/daily` | AI 일간 보고서 |
| GET | `/timeline/reports/weekly` | AI 주간 보고서 |
| GET | `/calendar?year=&month=` | 월별 증시 일정 |
| GET | `/calendar/{event_id}` | 일정 상세 |
| GET | `/heatmap?date=` | 섹터별 히트맵 스냅샷 |
| GET | `/heatmap/{sector}/news` | 섹터 관련 뉴스 |
| GET | `/news` | 뉴스 목록 (감성/섹터 필터) |
| GET | `/insights` | 규칙 기반 AI 인사이트 목록 |

외부 데이터 소스(한국투자증권/finlight/네이버 뉴스/FRED)는 API 키가 없어도 위 엔드포인트가 항상 동작하도록, 소스별로 "실 API 시도 → 실패 시 자동 폴백"을 구현했습니다.

**[구현 현황]** 초안에는 `/timeline/indicators` 1개만 "구현 완료"로 표기되어 있었으나, 현재는 위 13개 엔드포인트가 모두 구현되어 있습니다.

### 3.7 주요 설계 결정

- **도메인/데이터 선택 이유**: 상업적 재판매 목적 없이 크롤링 데이터를 그대로 노출하는 방식은 포트폴리오 프로젝트로 적합하지 않다고 판단해, "수집 데이터 + AI 인사이트"로 가치를 더할 수 있는 금융 시황 도메인으로 전환했습니다. 주식은 데이터 신뢰도와 팀의 도메인 이해도를 고려해 국내 상장사로 한정했고, 지표·뉴스는 "글로벌 맥락 속의 국내 시황"을 보여주기 위해 해외까지 포함했습니다.
- **DB 스키마 설계 이유**: 모든 테이블을 외래키 대신 "같은 날짜(date)"로 느슨하게 연결했습니다. 지표·뉴스·일정·섹터가 서로 다른 소스에서 비동기로 수집되기 때문에, 엄격한 FK 제약보다 date 매칭이 한 소스의 수집 실패가 다른 데이터 조회에 영향을 주지 않아 더 안전합니다. `DATABASE_URL` 하나만 바꾸면 SQLite → Supabase(PostgreSQL)로 전환되도록 설계했습니다.
- **LLM API 연동 방식**: 아직 팀에 LLM API가 지급되지 않아, 우선 규칙 기반(통계 z-score 이상치 탐지 + 감성 키워드 사전) 로직으로 인사이트를 구현했습니다. "데이터 → 문장" 변환을 별도 계층(`generator.py`/`report_generator.py`)으로 분리해, LLM 연동 시 그 부분만 교체하면 되는 구조입니다.
- **예외 처리 구성**: 모든 외부 수집기가 "실 API 우선 시도 → 실패 시 결정론적 샘플 데이터로 자동 폴백" 구조이며, 실패 시 예외 대신 로그로 원인을 기록하고 다음 단계로 진행합니다.
- **대시보드 지표 선정 이유**: 헤더 지표는 국내 투자자가 가장 먼저 보는 6개 지수·환율로 선정했습니다. 히트맵은 개별 종목 대신 대표 섹터 단위(6~9개, 가변)로 구성해 "지금 자금이 어디로 몰리는지" 큰 흐름을 먼저 이해시키는 것이 입문자의 학습 곡선에 자연스럽다고 판단했습니다.

**[구현 현황]** 초안에는 없던 절로, 실제 구현 과정에서 내린 설계 결정과 그 이유를 정리했습니다.
